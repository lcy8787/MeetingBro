# 微信輸入法 AI 錄音筆：MeetingBro 整合調研

調研日期：2026-11-10（香港時間）。範圍：公開產品資料、開發者文件及本地 MeetingBro 原始碼。未安裝或實測微信輸入法；未調用第三方橋接器；未變更應用程式或既有設定。

## 建議

以目前這部 Mac 及 MeetingBro 的本地優先架構，優先做「錄音 → 整理 → 可互動成果頁 → HTML 匯出」。保留現有 Whisper／Metal，將語音引擎替換與成果頁開發分開。

如果目的是直接使用微信輸入法識別：有 Windows 第三方實驗橋接可研究，但它沒有提供完整 AI 錄音筆，也未見現成 macOS 支援。如果目的是正式、跨平台接入騰訊語音能力：可使用公開的騰訊雲 ASR API，但沒有證據顯示它與微信輸入法使用同一模型或提供相同效果。

截至本次檢索，**未找到微信輸入法 AI 錄音筆對外公開的官方 API、SDK 或可移植模型權重**。這是檢索結果，不能據此斷言不存在商務合作介面。

## 2. MeetingBro 已經具備甚麼

以下來自本地目前檔案，而非只按 README 推測；程式碼存在不等於已通過完整實機驗收。

| 現有能力 | 位置 | 可以如何重用 |
|---|---|---|
| 麥克風、系統音訊、混合來源、WAV 檔案來源 | `app/backend/meetingbro/main.py` 的 `_build_audio_source`；`audio/` | 延續現有錄製入口；檔案來源可成為匯入功能基礎 |
| 正式 ASR 抽象與引擎工廠 | `asr/base.py`、`asr/factory.py` | 增加遠端或橋接識別器，無需重寫所有摘要流程 |
| Apple Metal／whisper.cpp | `asr/whisper_cpp_adapter.py` | 保留本機轉寫選項 |
| 滾動摘要、會議記憶、累積看板、精修稿 | `summarization/llm.py`、`session/manager.py` | 已有語音整理所需的主要文字處理層 |
| 會後章節、待辦及最終摘要 | `finalize_meeting`、`_emit_final` | 成果頁的初始內容 |
| 摘要、精修稿、看板及筆記分頁 | `app/frontend/src/App.tsx` | 整合為閱讀及查證更方便的會後頁 |
| 歷史、書籤、Markdown 匯出 | `storage/db.py`、`exporter.py`、前端歷史介面 | 延伸 HTML 匯出、主題導覽及原文跳轉 |

### 真正要補的缺口

1. **錄音保存與回聽。** 目前檢視的採集與工作階段流程未見完整音訊持久保存／回放介面。WAV 檔案讀入不等於錄音留存。要做點擊逐字稿回聽，需新增音訊檔、時間軸及播放器。
2. **可互動成果頁及 HTML 匯出。** 現有匯出以 Markdown／JSON 為主，可加一份獨立 `meeting.html`，支援章節導覽、搜尋、展開原文及待辦顯示。
3. **每條結論的來源。** 現有 `SummarySnapshot.source_segment_ids` 是快照層級；會後章節及待辦的快照更帶整場片段 ID 集合，未提供每條結論的精準依據。
4. **章節時間可靠度。** 現有會後 prompt 允許早期章節時間按壓縮記憶估算；不能直接把這些時間當成準確音訊定位。
5. **可信圖表資料。** 尚需具型別的圖表資料及原文來源，不能由任意摘要文字直接推測數據。
6. **跨裝置同步。** 現有 SQLite 是本機儲存；微信的裝置關聯不能直接套用。同步、帳號及分享服務應作另一階段設計。
7. **語言與呈現分離。** 現有語言型別主要為 `zh/en/de`，中文亦未明確區分繁簡及粵語來源。應把識別語言／方言與輸出語系分開，例如粵語識別、繁體中文整理；需要各引擎自行映射其支援代碼。

本地 `LOCAL_CHANGES.zh-HK.md` 記錄 Metal 路徑已完成部分短測，但長時間測試及退出問題尚未完成驗收。本次調研沒有恢復該項已暫停工作。

## 3. 三條整合路線

| 路線 | 實際接入內容 | 適合用途 | 判斷 |
|---|---|---|---|
| A. 自建錄音筆體驗 | 重用本地 ASR＋現有 LLM，加成果頁及 HTML 匯出 | 現有 Mac、跨平台產品、本地優先 | **首選** |
| B. 官方騰訊雲 ASR | 公開 WebSocket／SDK；摘要與網頁仍由 MeetingBro 做 | 想測試雲端中文、粵語及中英混講，接受音訊上雲 | 可選正式供應商 |
| C. 微信輸入法第三方橋接 | 調用正在運行的 Windows 輸入法語音服務，回傳文字 | 自用驗證、比較微信識別結果 | 僅作實驗選項 |

### 路線 C：確實找到可研究的橋接專案

[wechat-asr-bridge](https://github.com/kuxiaowo/wechat-asr-bridge) 的 [WETYPE 說明](https://github.com/kuxiaowo/wechat-asr-bridge/blob/main/docs/WETYPE.md) 提供 Windows x64 輸入法後端；文件列出的驗證版本為 3.0.0.34／3.0.0.37。

其本機介面使用 `POST /v1/audio/transcriptions`、模型別名 `wetype-voice`；支援檔案轉寫，但未提供串流輸出、時間戳、說話人分離或錄音筆的網頁生成。文件說明音訊仍由輸入法傳到服務端。

它依賴輸入法進程的原生功能及私有協議，不能視作官方 SDK。版本更新、網絡及認證狀態均影響可用性；本次未實測其穩定性。專案本身的開源授權也不代表騰訊授權再分發其客戶端、模型或服務。

**對目前 Mac 的含義：** 未見可直接使用的 macOS 後端。重做 Mac 原生橋接是新的逆向相容性工作，不能按「改一個 Base URL」估算。若使用另一部 Windows 電腦做遠端識別，也要另處理認證、傳輸及故障，已不是純本機方案。

### 路線 B：官方騰訊雲能力

[騰訊雲實時 ASR 文件](https://intl.cloud.tencent.com/zh/document/api/1118/53937) 列有普通話、粵語、英語及混合引擎，返回識別狀態及時間資訊，並要求開通服務和簽名認證。[SDK 概覽](https://cloud.tencent.cn/document/product/1093/52554) 另列出錄音文件及實時等接入選項。

這條路可以跨平台接入，但應以同一批真實會議錄音比較準確率、延遲及費用；不能把它宣稱為微信輸入法同款模型。各引擎的語言、時間戳及其他能力須按選用介面核對。

## 4. 建議架構與修改位置

```text
音訊來源 ─┬─ 可選的原音保存 → 音訊資產／播放時間軸
          └─ ASR：本地 Whisper | 官方雲端 | 實驗橋接
                  ↓
           原始逐字稿（保留來源與時間）
                  ↓
           精修稿／章節／決策／待辦
                  ↓
           經驗證的結構化文件
                  ↓
           React 成果頁＋離線 HTML 匯出
```

### 第一階段：用現有引擎做成果頁

- 在 `schemas.py` 加入具型別的 `MeetingDocument`，同步前端 `types.ts`。欄位包含版本、標題、章節、決策、待辦、來源引用；圖表先作可選。
- 在 `summarization/llm.py` 擴展結構化輸出；在 `session/manager.py` 驗證並保存。每條決策及待辦攜帶自己的片段 ID，負責人和期限未被提及時保留空值。
- 長會議採逐章提取、保留片段引用，再彙總全場；不要只用壓縮記憶猜測每章的精準時間。
- 新增 `MeetingDocumentView.tsx`，提供「概覽、章節、原文、待辦」導覽。先做到章節跳原文，之後才加音訊回聽。
- 在 `exporter.py` 增加獨立 HTML 匯出。使用固定模板及經驗證資料，文字正確轉義；避免把模型輸出的任意 HTML／JavaScript直接放進有桌面能力的頁面執行。
- 原始逐字稿與整理稿分開保存，整理錯誤時可以回溯。待辦勾選若要跨次開啟保存，需明確設計本機狀態儲存，不能只修改畫面。

### 第二階段：音訊與日常入口

- 在音訊進入 ASR 隊列之前分出有界、非阻塞的保存管道，避免 ASR 過載丟片時原音也跟著丟失。
- 新增 `audio_assets`，記錄檔案、格式、長度及時間軸；明確處理暫停、繼續和切換來源。播放器按片段時間定位。
- 為現有 `file:` WAV 來源加可見的檔案選擇及錯誤提示；其他格式另加解碼，不能直接宣稱 MP3／M4A 已支援。
- 在 Electron `main.cjs`／`preload.cjs` 增加可設定快捷鍵、選單列／托盤入口及錄音狀態。分享先以 HTML 檔案完成；可撤銷的線上分享及同步另做。

### 第三階段：可替換 ASR

現有 `ASRAdapter.transcribe(...)` 是按音訊片段回傳結果的抽象。實驗橋接可以包裝成 `WetypeBridgeASRAdapter`；官方長連線串流 ASR 則宜另設 session 層，處理開始、音訊推送、修訂結果及結束，不應每個短音訊片段重開連線。

建議新增的設定名稱（**目前不存在，直接填入不會生效**）：

```ini
MEETINGBRO_ASR_PROVIDER=local
MEETINGBRO_ASR_BASE_URL=http://127.0.0.1:8766/v1
MEETINGBRO_ASR_MODEL=wetype-voice
```

橋接器使用 8766，可避免與目前 MeetingBro 預設 8765 衝突。這是 ASR 設定，不能填入現有 LLM Base URL 欄位；聊天摘要與音訊轉寫是不同介面。

接入實驗橋接時，還需：

1. 在 `asr/factory.py`、後端啟動／健康狀態及設定介面加入供應商選擇；保留原有本地引擎。
2. 先以會後檔案或較長片段做對照測試，再考慮近即時分段。不能把檔案介面宣稱為真正串流。
3. 回傳只有文字時，時間只能標為片段邊界估算；不要偽造詞級時間戳、說話人或可靠信心分數。現有必填 confidence 及品質判斷需要適配未知值。
4. 禁止把遠端橋接器當作可共用的 Whisper 預覽模型；現有 `whisper-streaming` 路徑應保留獨立的本地 Whisper，或關閉相應預覽。
5. 加入有界排隊、超時、取消及明示的本地降級，避免請求長期積壓或重複提交。只在選用雲端／橋接供應商時傳送音訊。

## 5. 開發順序與驗收

建議依序交付：

1. **成果頁 MVP：** 現有引擎 → 有依據的章節／決策／待辦 → React 閱讀頁 → 單檔 HTML。
2. **完整錄音筆：** 原音保存、回聽、檔案匯入及快捷入口。
3. **供應商比較：** 同一份普通話、粵語、英語及混講錄音測試本地與官方雲端；如有 Windows，再加入輸入法橋接對照。
4. **分享與同步：** 需求成立後再加入帳號、同步、分享撤銷及衝突處理。

MVP 驗收應包括：數字、否定句、人名和期限沒有在精修中變意；每條決策能定位原文；章節時間不把估算當精準；離線 HTML 能閱讀；不產生沒有來源的圖表數值。之後另驗證長錄音、暫停續錄、音訊時間軸、網絡失效及退出流程。

**本次交付僅為調研與落地設計。沒有實作、安裝、上傳會議內容或執行長時間測試。**
